# GitHub Actions trust and token behavior for pull requests

Verified against GitHub's official documentation and first-party changelog on 2026-10-02. This research records security constraints. It does not choose the project's CI topology.

## Event and credential boundaries

| Trigger | Workflow and default checkout source | Fork PR credentials and behavior |
| --- | --- | --- |
| `pull_request`, `pull_request_review`, `pull_request_review_comment` | The workflow comes from the PR merge commit. `actions/checkout` defaults to that merge commit. | Fork runs get a read-only `GITHUB_TOKEN`, no repository or organization secrets, and may wait for maintainer approval. The PR can change the workflow itself, so this is not a place to expose a model key. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure use of `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) |
| `pull_request_target` | Runs the workflow and default checkout from the base repository's default branch. Since 2025-12-08, its workflow file, `GITHUB_REF`, and `GITHUB_SHA` use the default branch regardless of the PR's base branch. | Receives the base repository's secrets and a read/write-capable token, including for public fork PRs. It can read PR data and comment, but must not execute PR code. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [2025 ref change](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/) |
| `workflow_run` after a PR workflow | The privileged workflow file must exist on the default branch; it starts after the named workflow completes. | Can access secrets and write tokens even when the upstream workflow could not. Treat upstream run metadata and artifacts as attacker-controlled. It is a privilege boundary, not evidence that the earlier run or its output is trustworthy. [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [secure use](https://docs.github.com/en/actions/reference/security/secure-use) |

GitHub recommends `pull_request` when secrets and elevated permissions are unnecessary. Its workflow is itself PR-controlled, which means a successful fork run still does not make that workflow suitable for a model credential. `pull_request_target` avoids running the PR's workflow by default; checking out and running the fork's code defeats that boundary. [Securely using `pull_request_target`](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

## Reading source versus running it

Reading a PR is not the same as executing it. A reviewer can resolve the PR's head repository and immutable `head.sha`, list changed files with the Pull Requests REST API, then fetch each blob through the Contents API using that commit SHA as `ref`. The REST API exposes PR file names and patches; the Contents endpoint accepts a commit ref. This keeps untrusted source as input text and avoids running build scripts, package hooks, tests, PR-supplied actions, or repository instructions. It does not make the text safe to follow: titles, descriptions, comments, file contents, and generated patches remain prompt-injection input. [List PR files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files), [get repository content](https://docs.github.com/en/rest/repos/contents#get-repository-content), [GitHub untrusted-input guidance](https://docs.github.com/en/actions/reference/security/secure-use)

The `actions/checkout` guard is useful but narrow. As of 2026-07-20, v7 blocks common fork head/merge checkout patterns in `pull_request_target` and in `workflow_run` when the upstream event is a `pull_request*`; GitHub backported this to supported floating major versions except v1. Specific SHA/minor/patch pins need their own upgrade. It does not block `git fetch`, `gh pr checkout`, unrelated third-party repositories, or downloaded artifacts. Do not treat a passing guard as permission to execute attacker-controlled code. [`actions/checkout` protection changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout/), [secure checkout guide](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

## Tokens, secrets, and gates

- Set workflow-wide `permissions: {}` and grant only needed scopes per job. Once a permission is named, omitted scopes become `none`. A fork `pull_request` cannot ordinarily gain write scopes; admins of private/internal repositories can opt to send write tokens and secrets to fork workflows. Those settings erase the normal fork boundary and should remain disabled. [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [repository Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)
- Public-repo fork approval defaults to first-time contributors. GitHub warns that a user whose commit or PR has ever been merged bypasses the first-time policy; the all-external-contributors policy is the stronger gate. This controls when an untrusted workflow runs, not whether its code is trusted after approval. [Fork workflow approval settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), [approve runs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks)
- Dependabot PR runs for `push`, `pull_request`, review, and review-comment events default to fork-like behavior: read-only token and no Actions secrets. Only Dependabot secrets are available. Explicit `permissions:` can raise the token scope for Dependabot, unlike ordinary fork PRs. Whether Dependabot reviews are included, excluded, or given a deliberately provisioned Dependabot secret and token policy remains a project choice. [Dependabot troubleshooting](https://docs.github.com/en/code-security/dependabot/troubleshooting-dependabot/troubleshooting-dependabot-on-github-actions)
- An environment with required reviewers can withhold its secrets until approval. This can gate an expensive review job, but it does not let an untrusted fork `pull_request` job receive repository secrets; the job must reference the environment, and a reviewer approval is still required. [Deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)

## Model credentials and publishing credentials

GitHub's event model cannot make a secret safe merely because the model is asked not to reveal it. If the model process shares a job with a model API key, a write token, or a shell/file-read tool, PR-controlled text can try to make that process disclose the credentials through logs, comments, network access, or tool output. GitHub's secure-use guidance warns that untrusted input in privileged workflows can expose secrets and write access; secret masking is not a guarantee against transformed or indirect disclosure. [Secure use](https://docs.github.com/en/actions/reference/security/secure-use)

If Actions jobs are used, keep the model credential in the review job and the `pull-requests: write` token in a separate publisher job. Steps in one job share runner state, so a step boundary is not credential isolation. An external durable host should enforce the equivalent process boundary. This does not require the primary review to use a schema: its findings can remain free-form Markdown. At the final publication boundary, validate the target PR and reviewed head SHA, ensure each inline comment path and line maps to the reviewed diff, and bound the number and size of comments and the final Markdown body. Preserve valid Markdown and inline anchors. The REST review API supports `event: COMMENT`; set `commit_id` to the exact reviewed head SHA so the result cannot appear current for a later revision. [REST review API](https://docs.github.com/en/rest/pulls/reviews), [secure use](https://docs.github.com/en/actions/reference/security/secure-use)

For publication, `GITHUB_TOKEN` with only `pull-requests: write` is sufficient when repo-scoped bot identity is acceptable. A GitHub App installation token is an alternative when a separate bot identity or selected repository access is needed; GitHub lets the minted token narrow repositories and permissions, and installation tokens expire after one hour. Keep the App private key away from the model job. [Workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [App installation tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token), [`create-github-app-token` in Actions](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow)

An external GitHub App webhook service can fetch PR contents by immutable SHA and hold the model runtime and publisher in separate services. This removes Actions event-specific token behavior from the execution path, but moves spend limits, abuse prevention, runtime isolation, and delivery retries into the service. It is a pattern to evaluate, not a topology decision made by this research.

## Workflow artifacts and remaining uncertainty

Never execute an artifact from an unprivileged PR workflow in a privileged `workflow_run`. If an artifact is unavoidable, treat it as attacker-controlled data, extract outside the workspace, validate its schema and bounds, and do not interpolate values into expressions or shell. For this review use case, the privileged stage can fetch PR state itself and does not need to trust artifacts for PR identity or source. [GitHub Security Lab: preventing pwn requests](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/), [GitHub Security Lab: new patterns and mitigations](https://securitylab.github.com/resources/github-actions-new-patterns-and-mitigations/), [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use)

Dependabot-triggered `workflow_run` credential behavior is not stated clearly in the official pages reviewed; do not infer that it has either Dependabot-only secrets or ordinary repository secrets without a controlled spike. This is an unresolved fact if the chosen policy includes that event. The remaining choices include whether the reviewer fetches source through GitHub's API or checks out a tree strictly as data, whether maintainers require approval before spend, whether Dependabot reviews are in scope, and whether a GitHub App service is already required by the separately settled durable-per-PR boundary. This research does not reopen that boundary or decide those product choices.
