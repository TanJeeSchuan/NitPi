# Pi Durable recovery, isolation, and external-effect guarantees

**Source pin:** `earendil-works/pi` commit [`221cbcb02e8d8ee0b11db8076d755b0dace03857`](https://github.com/earendil-works/pi/commit/221cbcb02e8d8ee0b11db8076d755b0dace03857), the `main` head returned by `git ls-remote` on 2026-10-02. The ticket and map contain no selected SHA. An earlier API lookup returned `4e69b0c28060f0f02fbe38bfa7c21a2e2eb25057`, but that commit does not contain `packages/durable`; the live `main` head does. Pi Durable marks its API experimental and subject to change without notice.

Each section separates the runtime fact from what an application must supply. These findings describe the inspected source only.

## Finding 1: Pi Durable commits its own state atomically; persistence depends on the chosen backend

**Runtime guarantee.** A Session serializes mutations through one commit line. A transaction can append conversation entries, edit typed documents, create tasks, and update task state as one storage batch. Storage backends must admit each batch atomically. The transcript and task checkpoints are durable only when backed by persistent storage; `MemoryStorage` is volatile. [Concepts and storage options](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L78) · [Session commit and storage contract](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1521) · [Backend guarantees](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L4188)

**Application obligation.** Choose and operate a persistent backend whose failure guarantees match the required recovery point. Pi's commit atomicity ends at that backend. It does not include model providers, GitHub, or other network services in the same transaction.

## Finding 2: Conversations persist transcripts and have independently configurable agent state

**Runtime guarantee.** A conversation is a durable transcript of immutable entries. `reset()` changes which prior entries the model sees; it does not delete old stored history. `fork()` continues from a selected parent entry and inherits the parent's agent configuration as of that entry. Each conversation stores agent choices in `pi.agent`, including model, thinking level, selected extensions and tools, instructions, and working directory. Unset choices resolve against host defaults. [Conversations and forks](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L388) · [Per-conversation agent](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L188) · [Agent state](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L421)

**Application obligation.** A conversation is a history and configuration scope, not a security boundary. The host supplies `env` for each call, using the conversation ID and `cwd`; the runtime does not create a sandbox or isolate credentials by itself. Environment state may change between a tool's original attempt and its recovery replay. [Environment](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L231) · [Tool environment and authorization boundary](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2631)

## Finding 3: Typed documents and conversation changes can share one transaction

**Runtime guarantee.** Pi Durable stores typed JSON documents beside transcripts. A document definition names its kind, version, scope, history policy, and fork behavior. Built-in documents include per-conversation agent choices, live run state, inbox submissions, and usage totals. A `Tx` can edit documents and transcript entries atomically; task creation and task checkpoints can join the same commit. `requestId` deduplicates a retried submission within its conversation before another write occurs. [Documents and application state](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L487) · [Document definitions](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L919) · [Submission idempotency scope](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2120)

**Application obligation.** Pick document scope, history, and fork policy to match the data's intended lifetime. `requestId` covers Pi submission admission only. It does not deduplicate a GitHub request or another external effect.

## Finding 4: Task checkpoints resume work after process recovery, but effects can repeat

**Runtime guarantee.** A durable task records a full checkpoint at each committed phase step. On open, a surviving `running` task returns to `pending` with its last checkpoint and is scheduled again. A task can commit `waiting` on child task IDs, then resume when those tasks settle. Task definitions are resolved from the current installed registry, so required task code and compatible migrations must be available for pending work to resume. [Task state and recovery](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1570) · [Reopen reconciliation](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1869) · [Child-task waiting](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L444)

**Application obligation.** A crash after an effect but before its outcome commit leaves the task in the intent phase. On recovery the handler cannot infer from Pi's checkpoint whether the effect happened. It must retry idempotently, query or poll the external system, or record that the outcome is uncertain. The task API does not promise exactly-once effects. [Effect sandwich](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1825)

## Finding 5: Tool replay is opt-in and governed by both stored and current declarations

**Runtime guarantee.** Before `execute()` runs, the tool task commits its final arguments and replay policy. Omitted `replay` means `unsafe`. After recovery, a tool replays only if both the stored policy and the currently resolved declaration allow `safe`; a current unsafe declaration can veto replay, while a current safe declaration cannot upgrade an earlier unsafe intent. Otherwise Pi records an `interrupted` error result with committed partial output. [Tool replay policy](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2631) · [Recovery replay decision](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2980)

**Application obligation.** Mark a tool safe only if repeating it is harmless or its arguments contain a stable idempotency key. Store generated values that must remain stable in the checkpoint, input, or durable memo. An external publication tool cannot be made safe merely by setting `replay: "safe"`.

## Finding 6: Pi supports parallel work and structured ownership, with explicit background boundaries

**Runtime guarantee.** Independent calls in a tool round run in parallel by default. The host can select sequential execution globally or a tool can require a sequential round. Custom tasks can create child tasks, wait for selected tasks, and receive durable outcomes. Owned foreground work keeps its owner live; aborts cascade down ownership edges. A background task is a boundary for ordinary cancellation and idle checks. [Tool execution settings](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L392) · [Parallel round scheduling](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L3461) · [Structured concurrency](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2031)

**Application obligation.** Ownership and scheduling define lifecycle, not filesystem, process, or credential isolation. Provide separate environments or containers where isolation is required. The documented storage contract allows one process to own a storage at a time and provides no cross-process lock. [Environment](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L231) · [Storage ownership](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L519)

## Finding 7: Caller cancellation, durable abort, and process close have different effects

**Runtime guarantee.** Cancelling a `Context` or a wait cancels that call or wait; it does not itself mark shared work aborted. `Conversation.abort()` withdraws queued inputs and marks foreground work reached by the ownership traversal. Close seals new work, signals active invocations, joins them, and closes storage without writing task outcomes; pending work resumes on reopen. Task, tool, or hook code that ignores cancellation can keep close pending. [Context cancellation and submissions](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L44) · [Abort and subagents](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L397) · [Scheduler abort and close](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1869)

**Application obligation.** Use the abort API when the requested meaning is durable cancellation. Decide separately whether explicitly background work should survive. Do not treat cancellation of a CI waiter or runner as proof that a remote effect or Pi task was stopped.

## Finding 8: GitHub publication needs application-level idempotency and reconciliation

**Runtime guarantee.** Pi gives the application a durable task intent, checkpoints, task receipts, and transactionally committed local documents and entries. It does not atomically commit with GitHub. A `requestId` protects Pi input admission only; it is not propagated to GitHub. GitHub's documented create-review and create-review-comment endpoints expose no idempotency key. A crash between GitHub accepting a post and Pi committing the response leaves the external outcome ambiguous. [Effect sandwich](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L1825) · [Pi submission request IDs](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L2175) · [GitHub create review](https://docs.github.com/en/rest/pulls/reviews?apiVersion=2022-11-28#create-a-review-for-a-pull-request) · [GitHub create review comment](https://docs.github.com/en/rest/pulls/comments?apiVersion=2022-11-28#create-a-review-comment-for-a-pull-request)

**Application obligation.** Persist a stable operation key and reconcile remote review/comment state before retrying. The key joins Pi's local intent to the GitHub objects the application finds during reconciliation; GitHub does not treat it as an idempotency token. If reconciliation cannot establish whether the first post succeeded, surface an ambiguous result instead of claiming exactly once. This is an application contract, not a Pi Durable guarantee.

## Finding 9: Backend settings determine which crashes an acknowledged commit survives

**Runtime guarantee.** SQLite uses WAL mode with `synchronous=NORMAL`; the docs state commits survive process crashes, while the newest commit may be lost on power or host failure. JSONL defaults to `fsync: false` and promises ordinary process-crash consistency. With `fsync: true`, it flushes sidecars before the commit marker, but does not flush the ordinary main-log marker, so an acknowledged tail commit may still disappear. [Storage options](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/README.md#L519) · [SQLite and JSONL contracts](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L4381) · [JSONL recovery and fsync](https://github.com/earendil-works/pi/blob/221cbcb02e8d8ee0b11db8076d755b0dace03857/packages/durable/docs/spec.md#L4398)

**Application obligation.** Align the deployment's durability promise with its backend, filesystem, and failure model. Atomic commit behavior does not imply that every acknowledged write survives host or power loss.
