# GitHub pull request review API constraints

Research date: 2026-10-02. Sources are GitHub REST and Actions documentation unless noted.

### Reviews group a summary with inline comments

`POST /repos/{owner}/{repo}/pulls/{pull_number}/reviews` creates one review record. Its optional `body` is the review summary and its `comments` array carries inline findings. The nested `comments` objects support `path`, `body`, `line`, `side`, `start_line`, and `start_side`, so modern line/range anchors work in the batched review request itself. `event` may be `APPROVE`, `REQUEST_CHANGES`, or `COMMENT`; omitting it creates a PENDING review that must later be submitted with `POST /reviews/{review_id}/events`. A direct `POST /pulls/{pull_number}/comments` creates an individual diff comment rather than a summary review. [Create a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) | [Submit a review](https://docs.github.com/en/rest/pulls/reviews#submit-a-review-for-a-pull-request) | [Create a review comment](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request)

### Inline comments must anchor to the PR diff

Create a comment with `path`, the head commit's `commit_id`, and a `line` present in the PR diff. `side` is `RIGHT` for additions or context and `LEFT` for deletions. For a range, `line` and `side` mark the last line and its side; `start_line` and `start_side` mark the first line and its side. `position` is a legacy diff offset and is documented as closing down; new publishers should use line and side coordinates. [Review comment parameters](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request)

### Anchors can become outdated as the PR changes

GitHub says using a `commit_id` other than the latest may render a comment outdated if a later commit modifies its target line. Review creation defaults `commit_id` to the latest PR commit when omitted; direct comment creation requires it. Returned comment objects include current and original commit and line/position fields, with `position` nullable, so consumers should retain the returned comment ID and inspect current anchor fields instead of assuming an old offset still identifies a live diff line. The docs do not promise that an old anchor can be reattached automatically. [Create a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) | [Create a review comment](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request) | [Review comment response fields](https://docs.github.com/en/rest/pulls/comments#list-review-comments-for-a-pull-request)

### The review endpoint batches comments, but publishes no batch cap

The review create body accepts a `comments` array, so one request can group several inline comments with one summary. GitHub's endpoint reference does not specify a maximum array length, per-comment character limit, request-body limit, or all-or-nothing behavior for a malformed batch. List endpoints separately cap `per_page` at 100; that pagination limit is not a documented write-batch cap. A bad anchor or other validation failure can return HTTP 422. [Create a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) | [List reviews](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request) | [Create a review comment](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request)

### Updates replace one known item's body; delete rules differ by item

`PUT /pulls/{pull_number}/reviews/{review_id}` updates the review summary body. `PATCH /pulls/comments/{comment_id}` updates one inline comment body. Both address an existing ID and require the replacement body, so repeating the same update does not create another review or comment. `DELETE /pulls/comments/{comment_id}` removes an inline comment. `DELETE /pulls/{pull_number}/reviews/{review_id}` only deletes a pending review; submitted reviews cannot be deleted. [Update a review](https://docs.github.com/en/rest/pulls/reviews#update-a-review-for-a-pull-request) | [Delete a pending review](https://docs.github.com/en/rest/pulls/reviews#delete-a-pending-review-for-a-pull-request) | [Update a review comment](https://docs.github.com/en/rest/pulls/comments#update-a-review-comment-for-a-pull-request) | [Delete a review comment](https://docs.github.com/en/rest/pulls/comments#delete-a-review-comment-for-a-pull-request)

### Create retries have no documented deduplication key

The review and direct-comment create endpoints are `POST` and expose no idempotency-key parameter. A caller that loses the response cannot assume a blind retry will be deduplicated; it may create another review or comment. The REST API provides list-reviews and list-review-comments endpoints for reconciling what GitHub accepted. Updates target an existing review or comment ID and replace its body, so retrying the same body against that ID updates the same object. GitHub documents that creating reviews triggers notifications and that rapid content creation can cause secondary rate limits. [Create a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request) | [Create a review comment](https://docs.github.com/en/rest/pulls/comments#create-a-review-comment-for-a-pull-request) | [List reviews](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request) | [List review comments](https://docs.github.com/en/rest/pulls/comments#list-review-comments-for-a-pull-request) | [HTTP method semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods)

### CI needs pull-request write permission

GitHub Actions' built-in token needs `pull-requests: write` to publish reviews and comments. A fine-grained personal access token or GitHub App token needs repository permission `Pull requests: write`. A workflow can set this at workflow or job level; once `permissions` is specified, unspecified permissions become `none`, so the publishing job must name the permission explicitly. Repository or organization token policies can further restrict the built-in token. [GITHUB_TOKEN permissions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/automatic-token-authentication#modifying-the-permissions-for-the-github_token) | [Workflow permissions syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions) | [Create a review token permissions](https://docs.github.com/en/enterprise-server@3.13/rest/pulls/reviews#fine-grained-access-tokens-for-create-a-review-for-a-pull-request)

### Rate limits matter most at publication time

GitHub documents a primary `GITHUB_TOKEN` limit of 1,000 REST requests per hour per repository, or 15,000 per hour for resources belonging to a GitHub Enterprise Cloud account. Secondary limits generally allow no more than 80 content-generating requests per minute and 500 per hour, and some endpoints have lower caps; a review request can trigger notifications and rapid writes may be throttled. On 403 or 429, follow `Retry-After` when present; otherwise GitHub says wait at least one minute for a secondary limit and use exponential backoff if it persists. [REST API rate limits](https://docs.github.com/en/rest/overview/rate-limits-for-the-rest-api#primary-rate-limit-for-github_token-in-github-actions) | [Secondary rate limits](https://docs.github.com/en/rest/overview/rate-limits-for-the-rest-api#about-secondary-rate-limits) | [Create a review](https://docs.github.com/en/rest/pulls/reviews#create-a-review-for-a-pull-request)

### Review-thread resolution uses GraphQL

GitHub's GraphQL `resolveReviewThread` mutation takes `ResolveReviewThreadInput`, whose required `threadId` is the thread node ID, and returns a `PullRequestReviewThread`; query `isResolved` to confirm the state. The thread object also exposes `viewerCanResolve` and `viewerCanUnresolve` as per-viewer capability fields. GitHub documents `unresolveReviewThread` as a separate mutation with required `threadId`, so a resolved thread can be reopened. The GraphQL mutation reference does not specify a fine-grained token permission for these operations. [Resolve and unresolve mutations](https://docs.github.com/en/enterprise-server@3.0/graphql/reference/mutations#resolvereviewthread) | [Required thread IDs](https://docs.github.com/en/enterprise-server@3.0/graphql/reference/input-objects#resolvereviewthreadinput) | [Current thread fields](https://docs.github.com/en/enterprise-server@3.22/graphql/reference/pulls#pullrequestreviewthread)
